# Plan: alerts for new places and price drops

## Goal
A student hears, in the app's bell, when a place they saved gets cheaper, and (if they ask for it) when a new place that fits them is listed.

## Feature
"New-listing alerts for students" (listed under Later in `docs/feature-list.md`; the owner asked for it now, with price drops). Done check: the team lowers the price of a saved place and lists a new fitting one; the student's bell shows one alert for each, and tapping it opens the place.

## How it decides
- **Price** means the same "from" price the cards show: the cheapest available room as a monthly figure (year / 12, semester / 6, rounded), or the student rate if that is lower.
- **Only bookable places**: no alert of either kind unless the listing is visible and has at least one available room, even if it has a student rate.
- **Price drop**: a real price cut only. The from price went down because a room's price or the student rate was lowered. Marking rooms full or free again, or adding a room, never counts. The student has it saved and has price alerts on. At most one unread drop alert per student per place (the database enforces it): on every save its "now" price is updated to the current one; it is removed if the current price is no longer below the "was" price, there is no bookable price, or the listing is hidden.
- **New place**: `residences.first_announced_at` is set the first time a listing is bookable. For 7 days after that, each team save matches again, so a fix (added university, corrected price) still reaches students who now fit. A small private record means nobody is told about the same place twice. Unread new-place alerts are removed if the listing stops being bookable or visible, or no longer fits that student. Only listings bookable today are marked as already announced by the migration, so there is no flood and today's drafts still get announced later.
- **Fits** (all must hold): the student switched new-place alerts on and has a budget saved; the price is within the budget (for a whole home, the rent split by its bedrooms, bills not counted); the listing names the student's university as nearby, when the student has a university saved; a women-only or men-only place goes only to students who stated that gender.
- **System alerts** have no person behind them: `actor_id` may be empty for these two types only, so no admin ID is shown and deleting an admin deletes no student alerts. The bell shows the Havenly mark. Alerts are deleted with their listing. The listing row is locked during a save so two saves cannot double-send.
- **After a listing is hidden**, an already-read alert that can no longer load its name reads "A place you were told about is no longer listed". The listing page already has its own "no longer listed" message.

## Steps
1. Database migration, tried first in a rolled-back test: two switches on `profile_private` (`alert_new_places` off by default, `alert_price_drops` on by default; no row counts as those defaults), `residences.first_announced_at` (filled only for listings bookable today, dated 8 days back so none re-matches), the private sent-record table, `actor_id` optional for the two new types, signed-in users limited to updating `is_read` on notifications, column grants for the two switches, notification types `new_place` and `price_drop` with `residence_id`, `old_price_aed`, `new_price_aed`, and a private function that `save_residence` calls to create alerts. `save_residence` notes the old from price before it writes. `schema.sql` updated to match.
2. Shared code and tests: alert types added to the bell's list, message wording in one tested helper, and a test table that the database from price equals the app's `priceInfo` for the same rooms.
3. Notifications screen (Havenly mark, hidden-listing wording): two new rows ("Marina Heights dropped from AED 3,200 to AED 2,900 a month", "New place that fits you: ..."), tapping opens the listing.
4. Profile: an "Alerts" block with the two switches. New-place alerts without a budget saved explains what is missing and links to Edit profile, and the block says women-only and men-only places are sent only if gender is set. The gender hint in Edit profile changes from "nowhere else" to also name these alerts.
5. Privacy policy (including the new gender use and the "last updated" date), demo sample data (one alert of each kind; switches blocked with the demo message).
6. Prove it with real temporary accounts (see Check 4), then delete the test data.

## Checks
1. typecheck, lint, tests, expo-doctor, export (web, iOS, Android).
2. Database (rolled back): a lower price alerts only savers with price alerts on; same or higher price alerts nobody; hidden listings alert nobody; two drops leave one alert with the first "was" price; a raise removes it; a new fitting listing alerts only matching students; over budget, other university, wrong or unstated gender and switch off get nothing; hide and show again sends nothing twice; a smaller raise updates the unread "now" price; full then free again alerts nobody; all rooms full with a student rate alerts nobody; a fix within 7 days reaches newly fitting students only; a student cannot create an alert or edit anything but its read mark, change another's switches, or call the alert function.
3. Saving a listing still works for the team in every case above, and existing enquiry notifications still arrive.
4. Real accounts through the public API, on the live database: first confirm no real student has new-place alerts on; use one listing clearly named as a test, which only temporary accounts save, plus one temporary admin. The team account adds it and lowers its price; the right student sees exactly those two alerts, the other none. The listing is public for a few minutes. Then delete the listing, its alerts and all temporary accounts, and confirm the counts match what they were before. No real listing is edited.
5. App at 390 px wide: bell dot appears, both messages fit, tapping each alert opens the listing, switches stay set after reload. Demo shows both sample alerts and blocks the switches.

## What could break
Step 1 changes `save_residence`, the only way the team saves a listing, and the notifications table that enquiry updates use. Both are re-tested. The price rule now exists twice (app and database); one shared list of example cases (no rooms, all full with a student rate, prices that need rounding) is run both by `npm test` against the app rule and by the rolled-back database test against the database function.

## Not doing
Phone push notifications (needs a development build), email or WhatsApp, a daily digest, alerts for saved searches with extra filters, price history, alerts for a newly added cheaper room on a listing nobody saved.
