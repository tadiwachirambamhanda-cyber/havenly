Overview

This document describes how Havenly is built today and what has to change technically before the v1 launch. It is the companion to the launch PRD, which covers what the product does and why.

Havenly is a React Native app built with Expo, backed by Supabase (Postgres, authentication, file storage and real-time updates). There is no custom server: the app talks to Supabase directly, and every rule about who can read or change data is enforced in the database itself.

Codebase at the time of writing: 35 screens and about 12,700 lines of TypeScript, 43 database migrations.

Architecture

Mobile app
  • Expo / React Native, iOS and Android
  • Web build used only for development preview
  • Session stored in the device keychain
Supabase
  • Postgres with row-level security on every table
  • Auth (email and password)
  • Storage for photos and videos
  • Realtime for messages, map and notifications
  • Hosted in Mumbai (ap-south-1)
Third parties
  • Mapbox GL JS, loaded in a WebView for the map
  • Google Fonts via Expo font packages, bundled
  • Sentry for crash reports, once its key is added
  • No analytics or ads

Design principles already in the code

  • The database is the security boundary. The app holds only the public Supabase key; row-level security decides what each user can see or change.
  • Privileged actions go through server functions. Anything involving eligibility, money or other users (claiming a perk, pinging someone, setting an enquiry status, saving a residence) runs as a database function that checks permissions itself.
  • Notifications are created by triggers, never by the app, so they can't be faked.
  • Data is fetched per screen when it comes into focus, with real-time updates where freshness matters. There is no global client store.

Navigation

The root stack picks one of three branches: signed out (log in, sign up, legal pages), signed in but not onboarded (onboarding), or the full app. The full app has five tabs (Feed, Discover, Housing, Inbox, Profile) and about thirty stack screens on top. Admin screens (Manage housing, enquiry pipeline, residence editor, brands, offers, events) sit in the same stack and are only linked from Settings for admin accounts; the database enforces admin-only access regardless.

State

Three React contexts: AuthContext (session and profile; signs out if the profile no longer exists), ThemeContext (system, light or dark) and ToastContext. Everything else is local screen state loaded on focus.

Data model

26 tables, grouped by area. Every table references profiles, which is one-to-one with the auth user and deleted with it.

Housing, in detail

  • residences: name, operator, area, address, coordinates, photos, amenities, nearby universities (curated by the team, not computed), gender policy, and whether it's shown to students.
  • room_types: name, price in AED, billing period (year, semester or month), occupancy, availability, order.
  • residence_partner_terms: referral fee % and partner contacts. Kept in its own table so it can be admin-only while residences stay public.
  • housing_enquiries: student, residence, room, question or viewing, move-in month, length of stay, budget, phone, message, viewing times, status (new, contacted, viewing booked, signed, lost), contract value, referral fee and when it was paid. The fee is saved at the moment a deal is signed, so later fee changes don't rewrite past deals.

Security

  • Row-level security on every table. Users read and write only what policies allow; for example, a student sees only their own enquiries, and only admins see partner terms.
  • Admin check: is_admin(), a database function reading profiles.is_admin. Admin status can only be set in the database, not from the app.
  • Server functions for privileged actions, each checking permissions itself: claim_offer, send_ping, toggle_post_like, toggle_interest, set_enquiry_status, set_referral_fee_paid, save_residence (one transaction for listing, rooms and terms), delete_own_account, bump_streak.
  • Who sees a check-in is decided by can_see_checkin(): the person themselves, mutual follows, shared group chats or shared communities.
  • Blocking is enforced in the database by is_blocked_between(), not only hidden in the app.
  • Storage: six public-read buckets (avatars, covers, post images, post videos, group icons, residence photos). Uploads are limited by folder ownership; residence photos are admin-only.
  • Keys: only the public Supabase key and the Mapbox token ship in the app, which is expected. The service-role key is never in the app.
  • Sessions are stored in the iOS and Android keychain via expo-secure-store (AsyncStorage on the web preview).
  • The map page escapes every name and title before inserting it into popups, so user-entered text can't run as code.

Key flows

Housing enquiry to referral fee

  1. The student sends an enquiry. Row-level security only accepts it with status "new" and no money fields.
  2. A trigger creates a notification for every admin; the bell updates live.
  3. An admin opens the enquiry, copies the lead to the residence, and moves it to contacted or viewing booked through set_enquiry_status.
  4. Each of those changes triggers a notification to the student.
  5. When the student signs, the admin enters the contract value. The function looks up the residence's fee % and saves the fee on the enquiry.
  6. When the residence pays, the admin marks it paid through set_referral_fee_paid. Manage housing totals fees owed and received.

Sign-up

  1. Email and password sign-up through Supabase Auth.
  2. A trigger (handle_new_user) creates the profile with a generated username.
  3. The app shows onboarding until interests are chosen or skipped, then the main app.

Map

The map is a self-contained HTML page rendered in a WebView, using Mapbox GL JS restyled to Havenly's palette in both themes. The app builds the page with offers, events, residences and visible check-ins embedded as data; pins cluster on screen as you zoom out.

The page and the app talk through messages: the page sends openOffer, openEvent, openResidence, ping and toggleInterest; the app sends back small updates (a new check-in, a changed count, a category shown or hidden) so the map never reloads and loses your position.

Because it runs in a native WebView, the map can't be shown in the web development preview; it's tested on a device or by generating the page directly.

Environments and deploys

  • One Supabase project (free tier) serves both development and the future production app. Free projects pause after a period without use and must be restored.
  • Configuration (Supabase URL, public key, Mapbox token) lives in app.json under extra.
  • Database changes are new migration files in supabase/migrations, applied with npx supabase db push --linked. An applied migration is never edited; fixes go in a new one. schema.sql is updated in the same change.
  • The app runs through Expo Go and the web preview. There is no EAS build configuration and no store build yet. Bundle identifier: com.havenly.app on both platforms.
  • Source control: private GitHub repository (tadiwachirambamhanda-cyber/havenly), pushed after every change.

Non-functional requirements

AreaRequirement
PrivacyNo analytics, ads or tracking SDKs. Location is requested only on screens that use it, foreground only. Check-ins expire after 4 hours.
SecurityEvery new table ships with row-level security in the same migration; privileged writes go through permission-checking functions.
PerformanceLists render skeletons while loading and animate in with a calm ease-out; images use expo-image with caching. Real-time channels are filtered to what each screen needs.
AccessibilityLabels on icon-only buttons, enlarged tap areas on back buttons, contrast checked in both themes, respect for the system's reduced-motion setting.
ReliabilityMulti-table admin writes run in one transaction; optimistic UI rolls back with a message on failure.
Data locationHosted in India (ap-south-1), disclosed in the privacy policy.

Testing

Today every change is type-checked (tsc --noEmit) and tested by hand in the web preview with throwaway accounts, which are deleted afterwards. Security rules are checked by running queries as an ordinary signed-in user and confirming they're refused.

There are no automated tests and no continuous integration. See launch requirements below.

Launch requirements

T0-1Back up the codeDone
  • Private GitHub (or similar) repository with the full history pushed; pushed after every change.
T0-2Separate production from developmentOpen
  • A production Supabase project on a paid plan (no auto-pause, daily backups), with all migrations applied.
  • The current project becomes development; build profiles point at the right one.
  • Decide the production region (see open questions).
T0-3Store buildsOpen
  • EAS build configuration with development, preview and production profiles; Apple Developer and Google Play accounts.
  • Tested on real iPhone and Android devices: photo upload, video, map, location prompt, dark mode, staying logged in.
  • Store privacy declarations matching the privacy policy.
T0-4Account deletion fixesDone
  • Signed referral records kept in anonymised form; every upload folder cleared, including cover photos.
T0-5Crash reportingNeeds Sentry key
  • Sentry is wired in with personal data scrubbed and disclosed in the privacy policy, plus an error screen. Create a Sentry project and add its DSN to app.json to switch it on.

Soon after launch

  • Push notifications through Expo's push service, with device tokens stored per user and sent from a database trigger or edge function.
  • Basic automated checks in CI: type-check plus a few end-to-end tests of sign-up, enquiry and the admin pipeline.
  • Server-side filtering for map and inbox real-time events.
  • Privacy-respecting usage measurement for the PRD's metrics.
